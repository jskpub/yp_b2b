# 지원금/주문결제 페이지별 프로토타입 제작 프롬프트

> 각 페이지를 HTML/CSS/JS 프로토타입으로 만들 때 사용할 프롬프트 모음
> 원문 출처: `B2B 기업 독서 프로그램 운영 관련 개발 검토사항_20260911.docx`
> 원문에 없는 내용(화면 문구, 결제수단 종류 등)은 각 프롬프트에서 "미확정/임의 구성"으로 명시하도록 지정함

## 프롬프트 ① 도서상세 페이지

```
[역할]
B2B 기업 임직원 독서지원 플랫폼의 "도서상세" 페이지를 HTML/CSS/JS로 만들어줘.

[배경]
이 페이지는 지원금이 자동 계산되어 노출되는 화면이야. 도서는 "추천도서"와 "개인도서" 두 종류가 있고, 각각 지원금 계산 방식이 달라.

[지원금 계산 로직 - 반드시 이 공식 그대로 구현]
- 추천도서: 지원금 = 판매금액 × 100% (전액), 직원부담 0원
- 개인도서: 지원금 = MIN(판매금액 × 50%, 10,000원), 직원부담 = 판매금액 - 지원금

[예시 데이터 (그대로 사용)]
추천도서:
- 15,000원 → 지원금 15,000원 / 직원부담 0원
- 20,000원 → 지원금 20,000원 / 직원부담 0원
- 30,000원 → 지원금 30,000원 / 직원부담 0원

개인도서:
- 10,000원 → 지원금 5,000원 / 직원부담 5,000원
- 16,000원 → 지원금 8,000원 / 직원부담 8,000원
- 20,000원 → 지원금 10,000원 / 직원부담 10,000원
- 30,000원 → 지원금 10,000원 / 직원부담 20,000원

[화면에 꼭 들어가야 할 요소]
1. 도서 유형 뱃지 (추천도서 / 개인도서)
2. 도서 기본정보: 도서명, 저자, 출판사, 도서소개 (추천도서는 "추천사유" 항목 추가)
3. 개인도서인 경우: 종이책/전자책 선택 UI
4. 지원금 자동 계산 결과: 도서가격 / 회사지원금 / 직원부담금 3단 표시
5. 월 1권 제한 안내: "이번 달 신청 가능 여부" 상태 표시 (가능/이미 신청함)
6. 구매/담기 버튼 — 월 1권 초과 시 비활성화

[제약사항]
- 화면 안내 문구나 버튼 텍스트, 지원금 소진 시 메시지 등은 원문 문서에 명시되어 있지 않으니 네가 합리적으로 만들되, "이건 확정된 사양이 아니라 임의로 만든 문구"라는 걸 주석으로 남겨줘
- 인터랙티브하게 만들어줘 (가격 입력하면 지원금이 실시간 재계산되는 방식)
- 디자인은 깔끔한 커머스 스타일, 모바일 우선(반응형)
```

## 프롬프트 ② 장바구니 페이지

```
[역할]
B2B 기업 임직원 독서지원 플랫폼의 "장바구니" 페이지를 HTML/CSS/JS로 만들어줘.

[배경]
직원이 도서상세 페이지에서 담은 도서들(추천도서/개인도서 혼합 가능)을 보여주고, 지원금이 적용된 최종 결제액을 계산해서 보여주는 화면이야.

[참고 - 이 페이지의 근거는 원문에서 약하니 아래 원칙만 지켜줘]
- "개인도서" 시스템 기능 중 하나로 장바구니가 언급되어 있음 (추천도서도 장바구니를 거치는지는 불명확하니, 편의상 둘 다 담을 수 있게 만들어줘)
- 상세 UI 사양(다중선택, 합계 표시 방식 등)은 원문에 없으므로 일반적인 이커머스 장바구니 패턴을 따르면 됨

[지원금 계산 로직 - 도서상세와 동일하게]
- 추천도서: 지원금 = 판매금액 × 100%, 직원부담 0원
- 개인도서: 지원금 = MIN(판매금액 × 50%, 10,000원), 직원부담 = 판매금액 - 지원금

[화면에 꼭 들어가야 할 요소]
1. 담긴 도서 리스트 (도서명, 유형 뱃지, 도서가격)
2. 각 도서별: 회사 지원금 차감 표시 / 직원 부담금 표시
3. 개별 도서 삭제 버튼
4. 하단 합계 영역:
   - 총 도서가격
   - 총 회사 지원금 (마이너스 표시)
   - 최종 결제액 (직원이 실제 결제할 금액, 강조 표시)
5. 장바구니가 비었을 때 빈 상태 화면
6. "결제하기" 버튼 (장바구니 비었으면 비활성화)

[제약사항]
- 예시 데이터는 아래 도서 3~4개를 사용해줘:
  - 추천도서 18,000원, 개인도서(종이책) 20,000원, 개인도서(전자책) 25,000원
- 인터랙티브하게(삭제하면 합계 즉시 재계산)
- 모바일 우선 반응형
```

## 프롬프트 ③ 결제 페이지 (가장 중요)

```
[역할]
B2B 기업 임직원 독서지원 플랫폼의 "결제" 페이지를 HTML/CSS/JS로 만들어줘. 이 프로그램에서 가장 핵심적인 화면이야.

[배경 - 복합결제(Hybrid Payment) 시스템]
이 플랫폼은 "회사 지원금 + 직원 결제금액"을 하나의 주문번호로 관리하는 복합결제 구조야.

[원문 예시를 그대로 재현해줘]
25,000원짜리 도서를 구매하면:
도서금액: 25,000원
B2B 기업 지원금: 10,000원
직원 결제금액: 15,000원
─────────────────
최종 결제금액: 15,000원 (직원이 실제로 결제하는 금액)

[결제 프로세스 - 이 순서 그대로 반영]
상품 선택 → 지원금 자동 계산 → 회사 지원금 차감 → 직원 부담금 계산 → 직원 결제 → 주문 완료

[화면에 꼭 들어가야 할 요소]
1. 주문 요약: 담긴 도서별로 (도서금액 / B2B 기업 지원금 / 직원 결제금액) 3단 표시
2. "하나의 주문번호로 회사지원금+직원결제금이 통합 관리된다"는 안내 (가상의 주문번호 표시)
3. 총액 계산 영역: 총 도서가격 / 회사 지원금 합계 / 최종 결제액(직원 실결제액) 강조
4. 결제수단 선택 UI (신용카드/간편결제/계좌이체 등 - 원문에 명시 없으니 일반적인 옵션으로 구성)
5. 약관 동의 체크박스 → 체크해야 결제 버튼 활성화
6. "결제하기" 버튼

[반드시 화면에 노출할 미확정 이슈 안내 문구]
"기존 영풍문고 PG 구조에서 회사지원금+직원결제 복합결제가 실제로 지원 가능한지는 별도 확인이 필요합니다"
→ 이 문구를 주의 배너 형태로 화면에 넣어줘 (개발 착수 전 반드시 확인해야 할 리스크이기 때문)

[제약사항]
- 인터랙티브(도서 구성에 따라 총액 실시간 계산)
- 모바일 우선 반응형
- 결제 버튼 클릭 시 실제 PG 연동은 하지 말고, 클릭하면 "완료" 상태로만 전환
```

## 프롬프트 ④ 주문완료 페이지

```
[역할]
B2B 기업 임직원 독서지원 플랫폼의 "주문완료" 페이지를 HTML/CSS/JS로 만들어줘.

[배경]
결제 페이지에서 결제를 마친 직후 보여지는 화면. 이 페이지 자체의 상세 UI 문구는 원문 문서에 없으므로, 아래 "정산 데이터 필드"를 화면에 어떤 형태로든 확인 가능하게 보여주는 것이 핵심이야.

[정산 데이터 필드 - 이 항목들을 원문 그대로 반영]
Employee ID     → 직원 식별번호
Order ID        → 주문번호
Book ISBN       → 도서 식별
Book Type       → 추천/개인
Format          → 종이/전자
List Price      → 정가
Selling Price   → 판매가
Company Subsidy → B2B 기업 부담
Employee Payment→ 직원 부담
Order Date      → 구매일
Refund Status   → 취소/환불
Review Status   → 서평 작성 여부

[화면에 꼭 들어가야 할 요소]
1. 주문 완료 확인 메시지 + 주문번호
2. 주문 내역 (구매한 도서 목록, 각각 지원금/직원결제액 표시)
3. 위 정산 데이터 필드를 (표 또는 카드 형태로) 보여주는 영역 - 실제 서비스에서는 안 보여도 되지만, 프로토타입 단계에서는 "이 페이지가 어떤 데이터를 생성하는지" 확인하는 용도로 노출
4. 다음 액션 버튼 (예: 나의 주문 보기, 계속 쇼핑하기 - 원문에 명시 없으니 합리적으로 구성)

[반드시 화면에 노출할 미확정 이슈 안내 문구]
"지원금 적용 도서의 주문취소·반품·환불 시 회사 지원금 환수 기준은 아직 확인되지 않았습니다. 이 프로토타입에는 취소/환불 기능이 포함되어 있지 않습니다"
→ 주의 배너로 넣어줘

[제약사항]
- 이전 결제 페이지에서 넘어온 데이터(도서구성, 금액)를 그대로 반영해서 보여주는 구조로
```

## 공통 원칙

네 프롬프트 모두 아래 원칙을 공통으로 지켰습니다.

- **지원금 계산 공식은 원문 그대로** (추천도서 100%, 개인도서 MIN(50%, 1만원)) — 임의 변형 금지
- **원문에 없는 부분**(화면 문구, 결제수단 종류, 완료 페이지 UI 등)은 "확인 필요/미확정"이라고 프롬프트 안에서 명시해서, 프로토타입 제작자가 실제 사양처럼 착각하지 않게 함
- **§7, §8의 리스크** (PG 복합결제 가능 여부, 환불 시 지원금 환수 기준)는 결제·완료 페이지에 경고 배너로 반드시 노출하도록 지정
